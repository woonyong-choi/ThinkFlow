# 그림 종류

| 항목 | 값 |
|---|---|
| 상태 | 구현 |
| 관련 결정 | [그림 문법과 배치를 직접 맡고 D2 호환을 버린다](../decisions/2026-10-01-own-syntax-and-layout.md) |

## 요약

그림 종류는 구조 그림 밖의 세 가지, 순서 그림(`sequence`), 상태 그림(`state`), 데이터 관계 그림(`data`)의 선언과 시간 흐름 규칙이다. 줄, 낱말, 이름, 값 형식, 머리, 오류 규칙은 [그림 문법](figure-syntax.md)을 따르고, 이 문서는 종류마다 다른 점만 정한다.

## 동기

문서 스킬은 맥락 그림, 구성 요소 그림, 순서 그림, 상태 그림, 데이터 그림 다섯 가지를 쓴다. D2는 이 다섯 가지를 한 문법 안의 모양 설정(`shape: sequence_diagram`, `shape: sql_table`)으로 그려서, 순서 그림 안에서는 선의 뜻이 바뀌는데도 같은 줄 모양을 쓴다. 종류를 첫 문장에서 정하면 종류마다 허용하는 줄이 정해지고, 다른 종류의 줄을 섞는 실수가 오류로 나온다.

## 예시

### 순서 그림

```text
sequence
title "OAuth 인가 코드와 PKCE"

person user "사용자"
box app "앱"
box auth "인가 서버"
external api "리소스 API"

step "인가" "사용자가 인가 서버에서 직접 로그인한다"
  user -> app "로그인 누름"
  app -> auth "authorize?code_challenge"
  note auth "challenge = S256(verifier)"
  auth -> app "redirect ?code" dashed
step "토큰" "코드와 원래 비밀값을 함께 내야 토큰을 준다"
  app -> auth "token (code + verifier)"
  auth -> app "access_token" dashed
  app -> api "GET /me (Bearer)"
```

1. 참여자는 선언한 순서대로 왼쪽부터 놓인다.
2. 메시지는 적은 순서대로 위에서 아래로 놓이고, 모든 메시지가 처음부터 보인다.
3. 재생하면 박자마다 그 메시지 화살표가 밝아지고 점이 지난다.

### 데이터 관계 그림

```text
data right

table orders "orders" {
  id bigint pk
  user_id bigint
  status varchar
}
table payments "payments" {
  id bigint pk
  order_id bigint fk=orders.id
  amount "numeric(10, 2)"
}

step "결제" "결제 행은 주문 행을 외래 키로 가리킨다"
  light payments.order_id orders.id
  payments -> orders "order_id 1042"
```

1. 외래 키 `payments.order_id`에서 `orders.id`로 가는 선이 열과 열을 잇는다.
2. 첫 박자에 두 열이 밝아지고, 둘째 박자에 점이 외래 키 선을 지난다.

## 상세 설계

### 순서 그림

| 줄 | 뜻 |
|---|---|
| `person`, `box`, `external`, `store` | 참여자. 선언 순서가 왼쪽부터의 순서 |
| `step "이름" ["설명"]` | 단계 |
| `a -> b "메시지" [dashed] [time=2s]` | 메시지 하나. 한 줄이 한 박자이고 한 행이다. `dashed`는 응답 |
| `a -> a "메시지"` | 자기 자신에게 보내는 메시지. 오른쪽으로 돌아 나오는 고리 |
| `note id "글"` | 바로 앞 메시지 행의 참여자 옆 메모 |
| `say`, `wait` | [그림 문법](figure-syntax.md)과 같다 |

- 메시지는 시간 흐름 안에만 쓴다. 첫 `step` 앞의 메시지는 오류다. 순서 그림에서는 메시지 순서가 곧 그림의 위아래 순서라서, 선언과 시간 흐름을 나누지 않는다.
- 메시지는 선이 아니라 행이다. 그래서 같은 두 참여자 사이 같은 방향 메시지를 여러 번 쓸 수 있고, `a -> a`도 쓸 수 있다. 구조 그림의 선 규칙과 다르다.
- 메시지 글은 필수다. 화살표 위 라벨로 늘 보인다. 점에는 글 상자를 붙이지 않는다. 같은 글이 두 번 보이기 때문이다.
- `note`는 메시지 줄 바로 다음 줄에만 쓰고, 그 메시지의 보내는 쪽이나 받는 쪽 참여자만 가리킨다. 박자를 만들지 않는다. 그 밖의 자리는 오류다. 자기 자신에게 보내는 메시지 행이면 메모는 고리 반대편에 놓인다.
- 참여자 선언 순서가 처음 메시지를 보내는 순서와 다르면 경고다. 문서 스킬이 처음 보내는 순서로 놓게 하기 때문이다. 메시지를 보내지 않는 참여자는 보내는 참여자 뒤에 선언 순서대로 오면 된다.

### 상태 그림

| 줄 | 뜻 |
|---|---|
| `state id "이름"` | 상태 |
| `start id` | 처음 상태. 선언된 상태 하나를 가리키고, 채운 점에서 그 상태로 가는 선을 그린다. 없어도 된다 |
| `final id` | 끝 상태. 선언된 상태를 가리키고, 그 상태에서 겹원으로 가는 선을 그린다. 여럿 가능 |
| `a -> b "사건" [dashed] [quiet]` | 전이. 사건 글은 필수 |
| `group id "이름" [direction=right\|down] {`, `}` | 상태 그룹 |
| 시간 흐름 | 구조 그림의 이동, `light`, `say`, `wait`와 같다. 이동은 전이를 따라간다 |

- 자기 전이 `a -> a "사건"`는 상태 위에 고리로 그린다. 재시도와 대기처럼 같은 상태에 머무는 사건을 보이기 위해서다.
- 같은 상태를 `final`로 두 번 적으면 오류다.
- `start`는 없거나 하나다. 없으면 채운 점과 그 선을 그리지 않는다. 둘 이상이면 오류다. 시작점이 둘이면 읽는 출발이 갈리기 때문이다.
- 채운 점과 겹원으로 가는 선은 이동 대상이 아니다.
- 전이의 양 끝은 상태다. 그룹을 끝으로 쓰면 오류다. 그룹은 상태를 묶어 보이는 틀이고, 그룹에 들어가는 전이는 어느 상태로 가는지 정하지 않기 때문이다.
- 같은 두 상태 사이 같은 방향 전이는 하나다. 사건이 둘이면 `"start, resume"`처럼 한 글에 적는다.
- 상태 그림에 `show`, `clear`를 쓰면 오류다.

### 데이터 관계 그림

| 줄 | 뜻 |
|---|---|
| `table id "이름" {`, `}` | 테이블. 두 줄 사이에 열을 둔다 |
| `열 타입 [pk] [unique] [fk=테이블.열]` | 테이블 안 열 하나. 선언 순서가 위에서 아래 순서 |
| 시간 흐름 | 구조 그림과 같다. 이동은 외래 키 선을 따라간다 |
| `light 테이블.열 테이블` | 열이나 테이블 전체를 밝힌다 |

- 테이블 이름은 영어 소문자로 시작하고 영어 소문자, 숫자, `_`만 쓴다(`-`는 쓰지 않는다). 열 이름은 영문자로 시작하고 영문자(대소문자), 숫자, `_`를 쓴다(`userId`, `createdAt`). 실제 데이터베이스의 열 이름을 그대로 적기 위해서다. `fk=테이블.열`의 열 부분도 같은 규칙이다. 열 이름은 대소문자를 가리고 테이블 안에서만 겹치지 않으면 된다.
- 타입은 영문자, 숫자, `_`만 든 낱말 하나(`bigint`, `varchar`)이거나, 그 밖의 기호나 공백이 있으면 따옴표 글(`"numeric(10, 2)"`)이다. `varchar(255)`처럼 따옴표 없이 기호를 쓰면 오류다. 타입 자리에 `pk`, `unique`, `fk=`가 오면 타입이 빠진 것으로 보고 오류다.
- 테이블 사이 선은 `fk=`로만 생긴다. 따로 선을 적는 줄은 없다. 관계를 두 곳에 적어 서로 어긋나는 일을 막기 위해서다.
- `fk=`가 가리키는 열은 `pk`나 `unique`여야 한다. 같은 테이블을 가리키는 외래 키(자기 참조)는 테이블 오른쪽으로 돌아 나오는 고리로 그린다.
- 이동 `payments -> orders`는 적은 방향(`payments`에서 `orders`)의 외래 키를 먼저 찾고, 없으면 반대 방향의 외래 키를 거꾸로 따라간다. 고른 방향의 외래 키가 둘 이상이면 `payments.order_id -> orders.id`처럼 열까지 적어야 하고, 테이블 이름만 적으면 오류다. 고를 선이 언제나 하나여야 하기 때문이다.
- 외래 키 방향과 반대로 적은 이동(`orders -> payments`)은 구조 그림처럼 선을 거꾸로 따라간다.
- `show 테이블 "글"`은 테이블 아래 카드에 예시 행을 보인다. 카드 규칙은 구조 그림과 같다.

### 종류 사이 규칙

| 줄 | flow | sequence | state | data | chart |
|---|---|---|---|---|---|
| `person`, `box`, `external`, `store` | 선언 | 참여자 | 오류 | 오류 | 오류 |
| `decision` | 선언 | 오류 | 오류 | 오류 | 오류 |
| `group` | 선언 | 오류 | 선언 | 오류 | 오류 |
| `state`, `start`, `final` | 오류 | 오류 | 선언 | 오류 | 오류 |
| `table` | 오류 | 오류 | 오류 | 선언 | 오류 |
| `a -> b` 선언 | 선 | 오류 | 전이 | 오류 | 오류 |
| `a -> b` 시간 흐름 | 이동 | 메시지 | 이동 | 이동 | 오류 |
| `show`, `clear` | 카드 | 오류 | 오류 | 카드 | 오류 |
| `light` | 도형, 그룹 | 오류 | 상태, 그룹 | 열, 테이블 | 행, 점, 칸 |
| `note` | 오류 | 메모 | 오류 | 오류 | 오류 |
| `reveal` | 오류 | 오류 | 오류 | 오류 | 계열 |
| `step`, `say`, `wait` | 쓴다 | 쓴다 | 쓴다 | 쓴다 | 쓴다 |
| `series`, `rule`, `missing`, `data`, `row`, `point`, `cell`, `link`, `x`, `y`, `scale` | 오류 | 오류 | 오류 | 오류 | 쓴다 |
| `aspect` | 쓴다 | 오류 | 쓴다 | 쓴다 | 오류 |

- 표의 `오류`는 그 종류에서 그 줄을 쓰면 `{파일}:{줄}: "{줄 종류}" is not allowed in a {종류} figure. Remove the line or change the kind statement` 오류라는 뜻이다.
- 차트의 줄은 [차트](charts.md)에 있다.

### 요구사항

| 요구사항 | 검증 계획 |
|---|---|
| 문서의 모든 예시 원본이 오류와 경고 없이 읽힌다. | 예시 원본을 뽑아 `check --strict` 실행 |
| 종류 사이 규칙 표의 `오류` 칸마다 오류를 낸다. | 칸마다 원본 하나로 오류 여부 확인 |
| 순서 그림 메시지는 적은 순서대로 위에서 아래로 놓인다. | 메시지 행의 y가 줄 순서대로 커지는지 확인 |
| 상태 그림의 `start`는 없거나 하나다. | `start` 없음에서 점이 없고, 둘인 원본은 오류인지 확인 |
| 외래 키는 `pk`나 `unique` 열만 가리키고, 외래 키가 둘인 두 테이블 사이 이동은 열까지 적는다. | 두 원본의 오류 확인 |
| 외래 키 선은 두 열의 행 높이에 붙는다. | 선 양 끝 y와 열 행 가운데 y 비교 |

## 단점

- 순서 그림에서 병렬 메시지(`&`)를 쓸 수 없다. 동시에 일어나는 메시지도 한 행씩 적는다.
- 데이터 관계 그림에서 외래 키가 아닌 관계는 선으로 적을 수 없다.

## 미해결 질문

- 순서 그림에 활성 구간(참여자가 일하는 동안의 세로 막대)을 넣나, 메모로 충분한가.
